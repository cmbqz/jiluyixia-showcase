# 记录一夏 · 工程精选

一个**微信原生 + 云开发**的个人管理小程序，从零做到上线，累计 **305 次提交**、**19 个页面**、**163 个自动化测试**。

这个仓库不是完整源码，而是从真实项目里挑出来的**工程实践与设计决策记录**：一个中等规模小程序如何被拆解、如何防止改坏、如何在质量与包体红线之间取舍。

> 完整源码与后端逻辑不公开。本仓库只包含文档、设计说明与示例骨架。

---

## 项目概览

| 维度 | 数据 |
|---|---|
| 形态 | 微信原生小程序 + 云开发（5 个云函数） |
| 规模 | 19 个页面；JS 9,690 行 + WXML 3,024 行 + WXSS 2,827 行 ≈ **1.55 万行** |

| 上线门禁 | `preflight` 9 项检查，当前 **9 通过 / 0 失败** |

**核心能力**：一句话记账 / 待办（中文自然语言解析）、循环提醒、统计、课程表作息识别、订阅消息推送、AI 助手。

## 这个项目里最值得看的三件事

### 1. 一句话解析引擎（4,332 行）

用户输入「午饭 28」「昨天打车 35 块，明天记得交房租」这样的句子，系统要判断这是**记账 / 待办 / 习惯打卡 / 笔记**中的哪一类，并抽出金额、日期、分类、标签。

难点不在正则，在于**优先级冲突**：一句话里同时出现金额和时间时，到底是已花掉的钱还是未来的计划？项目用一条明确的优先级链解决：

```
多事件拆分 → 过去式消费 → 记账 → 未来规划 → 待办 → 习惯词 → 兜底笔记
```

设计细节见 [`docs/02-一句话解析引擎设计.md`](docs/02-一句话解析引擎设计.md)。

### 2. 不靠自律的防回归体系

这个项目踩过的坑很典型：**改一处，崩三处**。课程表调整一次作息，把另外四个页面的数据一起带歪；改一条记录的存储格式，账单页正常但统计页整页打不开。

所以质量保障做成了三层，详见 [`docs/03-测试与回归体系.md`](docs/03-测试与回归体系.md)：

| 层 | 作用 | 手段 |
|---|---|---|
| 单元测试 | 验证解析、计算、归类的正确性 | 163 个 node 脚本 |
| 二次回归取证台 | 验证**跨页面数据一致性** | 全量 `wx` 桩 + 真实 `Page()` 实例 + `setData` 断言 |
| 上线预检 | 捕获「跑起来才发现」「提审才被拒」的问题 | 9 项静态检查 |

### 3. 包体 2MB 红线下的取舍

微信小程序主包硬上限 2MB，超了传不上去。项目长期把余量压在 80KB 红线之上，逼出了一批具体决策：图标用字体而非图片、样式复用优先、公共逻辑下沉到 `utils` 按需引入。这是一条**会持续收紧的约束**，而不是一次性任务。

## 本仓库不含什么

明确划出边界，避免误解：

- ❌ 完整业务源码（19 个页面）
- ❌ 云函数实现（后端逻辑、推送链路、AI 代理）
- ❌ 任何密钥、AppID、云环境 ID
- ❌ 用户数据、真实账目、界面截图
- ❌ 可直接一键运行的完整应用

保留这些不是小气，是因为前三项属于**运行期资产**：密钥泄漏会直接产生费用，后端逻辑公开等于交付整套服务。文档和设计思路没有这个问题。
