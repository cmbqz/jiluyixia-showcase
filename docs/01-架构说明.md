# 01 · 架构说明

## 一句话概括

**数据在本地，能力在云端。**

业务数据（账目、待办、课程表、习惯）全部存在用户手机的 `storage` 里，不上传；云端只承担三类无法在客户端做的事：AI 推理代理、登录态换取、定时推送。整个项目**没有一行云数据库读写**。

这个选择决定的不是技术方案，而是产品承诺：用户不需要信任一个服务器。

## 分层结构

```
┌──────────────────────────────────────────────┐
│  pages/    19 个页面（WXML + WXSS + JS）      │  视图与交互
├──────────────────────────────────────────────┤
│  utils/    27 个模块                          │  领域逻辑
│    parser / localnlu / aiparse   解析         │
│    store / accountlib / statslib 数据与计算   │
│    schedule / habitslib / savinglib 业务      │
│    gaming / theme / iconskin     体验         │
│    privacy / share               合规与传播   │
├──────────────────────────────────────────────┤
│  config/    分类体系、版本号、能力开关         │  唯一配置源
├──────────────────────────────────────────────┤
│  storage    本地持久化（业务数据唯一落点）      │
└──────────────────────────────────────────────┘
              │ 仅在需要时调用
              ▼
┌──────────────────────────────────────────────┐
│  cloudfunctions/  5 个云函数                  │
│    aiParse     自然语言 → 结构化事件（AI 兜底）│
│    aiFigure    形象生成                       │
│    login       登录态                         │
│    morningPush 晨报推送                        │
│    taskRemind  定时任务扫描（每分钟触发）       │
└──────────────────────────────────────────────┘
```

**分层纪律**：`pages` 不直接碰 `storage`，一律经 `utils/store`。这条纪律是二次回归能成立的前提——只要页面走统一入口，测试就可以用内存 storage 替换真实环境，把整条链路跑起来。

## 19 个页面的分组

页面数量本身不是成就，分组清晰才是。按「离核心价值多远」分三层：

### 核心层（4 页）—— 用户 90% 的时间在这里

| 页面 | 标题 | 职责 |
|---|---|---|
| `home` | 记录一夏 | 首页；无 tabBar，用环绕式导航聚合当天入口 |
| `ledger` | 记账 | 一句话输入、账单流水、分类汇总 |
| `tasks` | 待办 | 一次性 / 循环 / 限时任务，到期提醒 |
| `morning` | 晨记 | 每日晨报，聚合天气、待办、账目摘要 |

### 功能层（6 页）—— 支撑核心场景

| 页面 | 标题 | 职责 |
|---|---|---|
| `stats` | 统计 | 收支趋势、分类占比 |
| `calendar` | 日历 | 按日期回看与补录 |
| `schedule` | 日程 | 课程表识别（拍照 / 粘贴 / 手录）+ 作息推导 |
| `habits` | 习惯打卡 | 习惯注册与连击 |
| `saving` | 攒钱罐 | 目标与进度 |
| `billimport` | 导入账单 | 微信 / 支付宝 CSV 导入，预览 + 去重 |

### 外围层（9 页）—— 支撑与治理

| 页面 | 标题 | 职责 |
|---|---|---|
| `profile` | 我的 | 个人中心聚合入口 |
| `settings` | 设置 | 设置总入口 |
| `data` | 数据管理 | 导出、清理、迁移 |
| `system` | 系统设置 | 推送、隐私、关于 |
| `location` | 设置位置 | 天气所需的位置授权 |
| `theme` | 主题 | 外观切换 |
| `icons` | 图库 | 分类图标 |
| `figure` | 形象坊 | 角色形象 |
| `trash` | 回收站 | 软删除与恢复 |

> 外围层不是「不重要」，而是**不该出现在第一眼**。19 个页面如果平铺给用户，等于没有重点。

## 数据流

以「说一句话记一笔」为例：

```
用户输入「午饭 28」
   │
   ├─▶ localnlu.parseMulti()         本地规则引擎，优先
   │      ├ 归一化：口语金额 → 数字
   │      ├ 掩码：时间表达先摘出，避免被当成金额
   │      ├ 切分：多事件拆分
   │      ├ 分类：关键词 + 优先级链
   │      └ 置信度判定
   │
   ├─ 置信度足够 ──▶ 直接落库（不联网，毫秒级）
   │
   └─ 置信度不足 ──▶ 云函数 aiParse ──▶ 结构化结果
                         │
                         └ 失败/超时 ──▶ 回落本地规则引擎结果
```

**关键设计：本地优先，AI 兜底，规则永远在。** 断网、云函数超时、AI 额度耗尽，记账都不能不可用。这条约束逼出了整个 4,332 行解析引擎的存在理由——它不是「AI 的廉价替代」，而是**主路径**。

## 云函数的边界

只有 5 个，且每一个都对应一件客户端**做不了**的事：

| 云函数 | 为什么必须在云端 |
|---|---|
| `aiParse` | 模型调用需要密钥。密钥放客户端会被打包进小程序包，反编译即可提取 |
| `aiFigure` | 同上，且涉及图片生成 |
| `login` | 换取登录态必须服务端参与 |
| `morningPush` | 发订阅消息必须服务端调用 |
| `taskRemind` | 定时器只能服务端跑 |

这条边界被写进了代码注释里（`parser.js` 文件头明确标注：「Key 填进前端会被打包进小程序、反编译即可提取，属安全事故」），因为**违反它的代价是真实费用**，不是风格问题。

---

## 一个被反复验证的取舍：不做云数据库

初期考虑过把账目同步到云端，最终没有做。理由：

1. 记账是**强隐私**数据，上云就要写隐私政策、要过审、要担责；
2. 单人使用场景下，多设备同步不是高频需求；
3. 不上云意味着**没有服务端成本随用户增长**，模型极轻。

代价也明确：**换手机数据不自动跟着走**，靠导出/导入迁移。这是一个被接受的产品妥协，不是遗漏。

## 目录约定

```
miniprogram/
  app.js / app.json / app.wxss
  config/         唯一配置源（分类体系、版本、开关）
  pages/<name>/   同名四件套（.js .json .wxml .wxss）
  utils/          领域模块，全部 CommonJS
  assets/         图标与角色素材
cloudfunctions/<name>/   index.js + package.json + config.json
tests/             163 个断言脚本
tools/             61 个工具（回归取证台、上线预检、批量修复等）
docs/              设计与过程文档
```

约定两条：**页面目录名 = 页面标题的文件名前缀**（便于 `preflight` 校验注册一致性）；**换行符统一 LF**，仓库内 `.gitattributes` 强制，否则「改 3 行」在 diff 里会显示成整文件重写。
