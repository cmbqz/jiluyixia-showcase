# 02 · 一句话解析引擎设计

> 输入一句话，输出结构化事件。看起来是个正则问题，实际上是一组**互相冲突的判断题**。

模块构成：`parser.js`（1,920 行，规则引擎）+ `localnlu.js`（1,283 行，本地模型层）+ `aiparse.js`（1,129 行，AI 链路与裁决），合计 **4,332 行**。

---

## 一、核心难题不是"识别"，是"归类"

用户说「明天记得交房租 2000」，这里面有：
- 金额（2000）
- 时间（明天，未来）
- 金额 → 直觉上是「记账」

但正确答案是**待办**。因为钱还没花。

同理「昨天午饭 28」有金额有时间，是记账；「跑步 30 分钟」有数字，是习惯打卡；「看了个电影」无金额无时间，是笔记。

**同一组特征，四种答案。** 所以引擎的第一性问题不是抽取得准不准，而是**判定优先级**。

---

## 二、优先级链（v2.3）

```
0  多事件拆分          一句话里有多笔 → 先切开再分别处理
1  过去式消费          吃了 / 花了 / ¥ 前缀 → 记账
                       餐饮类按时间段分早/午/晚餐
2  未来规划            明天 / 周末 / 打算 → 待办（即使含金额）
3  无时间无金额但有钱数 → 记账
4  习惯词              打卡 / 跑步 / 健身 → 打卡
5  规划动词            记得 / 开会 → 待办
6  兜底                笔记
```

几个刻意的设计：

**为什么「未来规划」排在「记账」后面却高于「无时间有金额」？**
因为顺序是按"特征强度"排的，不是按业务重要性。过去式消费有最强的确定性（已经发生了）；未来规划有次强的确定性（明确说了时间）；纯粹的金额最弱。

**为什么多事件拆分必须在最前？**
「早饭 5 块，晚饭 30」如果先跑归类，整句会被判成一个餐饮记账，金额取到 5 或 30，另一笔直接丢失。拆分必须先于一切判断。

**为什么习惯词排在规划动词之前？**
「每天跑步」既可以理解成习惯，也可以理解成待办。排前面的赢，这里选了习惯——因为习惯有连击奖励机制，误判成待办会让用户丢掉连击，比反过来更伤。

## 三、量词白名单：一次结构性返工

这是项目里最有代表性的一个修法。

### 问题

「盒仔茶」「盘心」「杯面」这类词，如果按「带量词就把量词剥掉」的规则处理，会被啃坏：

```
盒仔茶 12  →  仔茶 12     ❌ 商品名被毁
```

第一版的做法是**黑名单**：列举"哪些量词不能剥"。这个思路注定失败——黑名单是开放集合，永远有表外的说法击穿它。

### 修法：方向反转

从「不枚举哪些不能剥」改成「**只剥能确认该剥的**」。

每个量词配一份**它真正会计量的品类名词白名单**：

```js
// 示例（节选）
var QW_NOUN = {
  "杯": "咖啡|奶茶|水|豆浆|果汁|可乐|茶|酸奶|冰淇淋|酒|牛奶",
  "碗": "面|牛肉面|拉面|饭|汤|粥|米饭|馄饨|饺子|粉|米线",
  "盘": "炒饭|菜|水果|饺子|虾|烤肉|凉菜|点心|炒面",
  "盒": "牛奶|月饼|鸡蛋|饼干|巧克力|药|纸巾|酸奶|蛋糕",
  "台": "电视|电脑|洗衣机|空调|冰箱|手机|笔记本|显示器",
  "双": "鞋|鞋子|袜子|筷子|手套|拖鞋|球鞋|运动鞋|凉鞋"
};
```

只有当量词后面跟的名词**命中该量词的白名单**时才剥；否则原样保留。

### 背后的原则

| 失败模式 | 后果 | 严重性 |
|---|---|---|
| 漏剥（该剥没剥） | 账目名多带个量词，观感差 | 低，可接受 |
| 误剥（不该剥剥了） | 商品名被破坏，数据损坏 | 高，不可逆 |

**两类错误的代价不对称，所以默认选代价小的那一侧。** 这条红线被写进代码注释：只往白名单加词，禁止改回黑名单式负向断言。

## 四、日期归一：在入口修，不在下游修

### 问题

输入法会在数字后自动补空格，用户打出的是「11 月 3 号」。而下游所有日期正则是 `\d{1,2}月\d{1,2}号`（不带空格），整条失配。

后果：月份被丢掉，日期算成本月 3 号。**用户完全看不出哪里错了。**

### 修法

在**解析最前面**加一层归一，把 `数字 + 空格 + 月/日` 压回紧凑形态：

```
"11 月 3 号"  →  "11月3号"
```

### 为什么不在下游修

下游有十几处日期正则。逐条加 `\s*` 意味着：
- 改十几处，改漏一处就又坏一次
- 以后新写的正则还是容易漏
- 同一个 bug 有十几个可能的复发点

**在唯一入口修一次，所有下游一次性受益。** 这是一个通用模式：当一个问题会在 N 个地方复发，修那个共同的上游，而不是修 N 个下游。

## 五、本地模型层：5 层递进

`localnlu.js` 在规则引擎之上加了 5 层处理，每层解决一类问题：

| 层 | 名称 | 解决什么 |
|---|---|---|
| **L0** | 归一化 | 口语金额转数字：`二十来块` / `八十多` / `一百二` / `一块五` |
| **L1** | 意图直取 | AA 代付拆账、课表文本转循环任务、周期任务（每天 / 每周X / 每隔N小时）、限时任务 |
| **L2** | 掩码 | `H:MM`、`第N大节`、`N-M节` 先摘出，避免被金额匹配吞掉 |
| **L3** | 智能切分 | 无标点无空格的多事件：用金额锚点 + 段首词保守切分（`5块一斤` 不能误切） |
| **L4** | 后处理 | 分类名归一到配置分类表；餐次降级为标签（分类=餐饮 + 标签=午餐） |

**L2 掩码层值得单独说**：`第3大节`、`8:00-9:40` 这些课程表表达里含数字，如果不先掩掉，金额匹配会把 `3` 和 `8` 当成钱。掩码的本质是**先声明哪些片段不参与后续解析**，比写更复杂的排除正则可靠。

## 六、置信度裁决：什么时候该找 AI

不是所有输入都值得调用模型。`isLowConfidence(text)` 返回 `{confident, reason}`，只有判为低置信时才走 AI 链路。

判据方向：**能明确归类的不问 AI；有歧义、多解、词表外说法的才问。**

这样做的收益：
- 绝大多数输入零网络延迟、零费用
- AI 额度集中在真正难的长尾上
- AI 不可用时，降级路径已经存在（规则引擎结果）

---

## 七、验证方式

解析引擎的测试不在「跑通就完事」，而在**语料规模**：

- 批量语料测试：2,000+ 句真实表达
- 四套大数据回归，138 条结构化断言
- 量词专项：19 类量词的边界样例
- 修复回归：每个真 bug 都固化成一条永久断言

最后一条是纪律：**bug 修完必须留下断言**，否则同一个坑会在半年后重新踩一遍。
