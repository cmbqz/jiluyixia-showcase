# 04 · 踩坑复盘

> 五个真实 bug。重点不是"修了什么"，而是**为什么会发生**、**为什么只有这种修法不会再犯**。

每个案例按同一模板：现象 → 定位 → 根因 → 修法 → 沉淀。

---

## 案例一：用户说"输 5 笔只看到 3 笔"

### 现象

用户一次输入 5 笔账（如「早饭 5 块，午饭 28，打车 15，买水 2，晚饭 40」），反馈"只记进去 3 笔"。

### 定位

用回归取证台跑 3 / 4 / 5 / 7 笔输入，**全部正确落库**。存储里条数完全对，一个没丢。

真正的问题在回执提示：

```
Toast 提示框最多显示两行，超出部分被截断
5 笔的正文共 33 字 → 用户只看到前两行
```

### 根因

**把"数据显示不全"误判成"数据丢失"。** 这是一个诊断方向的错误，如果按"丢数据"去查存储层，会查很久且查不到东西。

### 修法

区分两类问题再动手：
- 数据层问题 → 查落库、去重、覆盖
- 展示层问题 → 查截断、折叠、条件渲染

本例是展示层。修回执文案/展示方式即可，**不该动存储逻辑**——动了就是给没病的地方开刀。

### 沉淀

诊断的第一步永远是：**先确定数据到底在不在**。用取证台直接读存储，比读代码猜快得多。

> 这个案例至今在待修清单里，因为还缺一个关键输入：用户当时到底看到几条。**没有这个数字，就不能确定是纯展示问题还是真有边界丢失。**

## 案例二：量词黑名单被"盒仔茶"击穿

### 现象

「盒仔茶 12」被解析成商品名「仔茶」，金额 12 正确但名称被破坏。

### 根因

第一版规则是**黑名单**：枚举"哪些量词不能剥"。黑名单是开放集合，永远存在表外说法。

### 修法

方向反转：不枚举「哪些不能剥」，改成**只剥「能确认该剥的」**。每个量词配一份"它真会计量的品类名词"白名单，命中才剥。

### 沉淀

两类错误的代价不对称：

| | 后果 | 可逆性 |
|---|---|---|
| 漏剥 | 名称多个量词，观感差 | 可逆，用户能改 |
| 误剥 | 商品名损坏 | 不可逆，原始信息丢失 |

**当两类错误代价不对称时，默认选代价小的那一侧。** 这条已写进代码红线：只许往白名单加词，禁止改回黑名单式负向断言。

## 案例三：改一条记录，另一个页面整页打不开

### 现象

新增记录字段后，账单页正常，统计页整页白屏。

### 定位

统计页在 `onShow` 里遍历全部历史记录做汇总。旧记录没有新字段，读取时得到 `undefined`，参与运算后抛出异常，整页渲染中断。

### 根因

**旧数据不满足新代码的数据契约。**

这是一个结构性缺口：单元测试里造的数据永远是"当前格式"的，所以这类 bug **在单测里永远测不出来**。

### 修法

两层：
1. **读取侧防御**：所有历史数据读取点做字段兜底，缺字段给默认值而不是让 `undefined` 流下去
2. **迁移侧归一**：在数据入口做一次格式升级，把旧记录补齐到当前格式

### 沉淀

**数据格式变更必须同时考虑"已存在的用户数据"。** 这不是兼容性问题，是"代码一上线就崩"的问题。

新增断言：用旧格式数据跑一遍所有页面 `onShow`，不许抛错。

## 案例四：导入账单把本机记录覆盖了

### 现象

从微信/支付宝导出 CSV 导入后，本机原有记录被顶掉。

### 根因

去重键选错。用「日期 + 金额」做去重键时，同一天同金额的两笔不同消费被判定为"重复"，导入逻辑选择了覆盖而非跳过。

### 修法

1. 去重键改为组合键（含备注/对方/流水号等更细的维度）
2. 导入流程加**预览层**：先展示"将新增 N 笔 / 跳过 M 笔重复"，用户确认后才写入
3. 导入前自动快照，可回滚

### 沉淀

**批量写入是不可逆操作，必须有人工确认环节。**

`预览 → 确认 → 写入 → 可回滚` 这个四段式，后来成了所有批量操作的标准模板。

## 案例五：同一份课表导两次，节次翻倍

### 现象

用户重复导入同一张课程表，结果每天节次变成两倍。

### 根因

课表导入按"追加"语义实现：每次导入都往数组里 push，没有判断"这节课是不是已经有了"。

### 修法

导入语义从**追加**改为**整张替换**：一次导入 = 一份完整课表，先清空再写入。

配套变化：
- 导入前提示"将替换现有课表"
- 支持"仅导入到空表"的保守路径，避免误覆盖手调过的作息
- 课表链路独立护栏（9 套，单套最多 6,340 条断言）

### 沉淀

**同一个数据结构有两种合法语义（追加 / 替换）时，必须显式选一个，并且让用户在操作前知道选的是哪个。**

默认行为选错，用户每重复一次操作就多一份垃圾数据。

## 六个案例之外，一条方法论

回头看这五个坑，能归纳出一条：

> **大多数"改坏了"，不是逻辑写错，而是对"输入是什么样"的假设错了。**

- 假设历史数据是新格式 → 崩
- 假设用户不会重复操作 → 数据翻倍
- 假设黑名单能覆盖所有说法 → 被表外词击穿
- 假设回执能显示全部内容 → 被当成丢数据
- 假设去重键唯一 → 覆盖真实记录

所以防御的位置也很清楚：**在边界处不信任输入**。读存量数据要兜底，批量写入要预览，开放集合要用白名单而非黑名单。

这也是为什么这个项目最终长出了三层质量网——不是一开始规划的，是被这五个坑一个一个打出来的。
