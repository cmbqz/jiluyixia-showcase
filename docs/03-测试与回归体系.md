# 03 · 测试与回归体系

> 小型项目的质量保障不该靠自觉，该靠**让错误无法通过**。

这个项目的规模：163 个测试脚本、61 个工具脚本、305 次提交。规模不大，但迭代密度高——上线前后持续改动，且改动集中在**共用底层**（解析引擎、store、分类体系），一处出错会横跨多个页面。

---

## 一、为什么需要三层

不同的错误类型，只能在不同的层被发现：

| 错误类型 | 例子 | 哪一层能发现 |
|---|---|---|
| 逻辑算错 | 金额加总少了一笔 | 单元测试 |
| 跨页面不一致 | 改了记录，账单页对但统计页没更新 | **二次回归** |
| 环境/配置错误 | 页面漏注册、图片路径错、包体超限 | **上线预检** |

只做单元测试，第二类错误完全漏掉——因为「数据在四个页面之间是否一致」不是任何单个函数的性质。

---

## 二、第一层：单元测试（163 个）

普通 node 脚本，`node tests/xxx.test.js` 直接跑，不需要微信开发者工具。

覆盖重点：
- **解析引擎**：语料批量断言、量词边界、优先级链、日期归一
- **计算逻辑**：统计汇总、攒钱进度、习惯连击、循环任务展开
- **数据层**：store 的增删改查、软删除与恢复、导入去重

约定：**每个真 bug 修完都固化成一条永久断言。** 这条纪律让测试套件随修 bug 单调增长，而不是靠人想起"要补个测试"。

---

## 三、第二层：二次回归取证台

这是整个体系里最值得讲的部分。

### 问题

回归用例里一大半不是「输入一句话看解析结果」，而是：

> 改一条记录 → 打开另外四个页面 → 看它们是不是同一份数据。

只读代码回答不了这个。必须**真的把页面的 `onShow` 跑起来，读 `setData` 之后的值。**

### 做法

`tools/_regress-harness.js`（270 行）建了一套完整的运行环境：

```
1. 全量 wx 对象桩
   ├ 内存 storage（getStorageSync / setStorageSync 直接读写内存对象）
   ├ 导航 API（navigateTo / switchTab / reLaunch）
   ├ 交互 API（showToast / showModal / showActionSheet）
   └ 选择器查询、Canvas 上下文（Proxy 桩，任何方法都返回自身）

2. Page() 捕获
   Page(cfg) 不真渲染，只把 cfg 存下来

3. 实例构造
   Object.create(cfg) 造实例 + data 深拷贝
   setData 支持 'a.b.c' 路径写法

4. page("tasks")
   调用 onLoad / onShow，把异步链跑完，返回实例

5. send(cmd, text)
   走首页真实链路：强制前缀 + parseMulti
```

### 关键点：走真实链路，不 mock 业务

`send()` 不直接调用解析函数，而是模拟用户从首页输入。这意味着桩只打在**平台边界**（`wx.*`），业务代码全部真跑。

这是刻意的取舍：
- 打了业务桩 → 测的是桩，不是代码
- 只打平台桩 → 测的是真实链路，但需要把 `wx` 的全部 API 都补全

`wx` 的桩必须够全，否则页面会因为「某个 API 不存在」直接抛错，测出来的失败是假失败。

### 为什么不进测试套件

harness 是**取证台**，不是断言集合。它用于出报告——当怀疑某处数据不一致时，用它把链路跑一遍看实际值。

> 这个区分很重要：单元测试回答「是否符合预期」，取证台回答「实际发生了什么」。

## 四、第三层：上线预检（9 项）

`tools/preflight.js` 检的是**「跑起来才发现」和「提审才被拒」**的问题，普通单测覆盖不到：

| 检查项 | 不检查的后果 |
|---|---|
| 页面注册与实际目录一致 | 漏注册 = 点进去白屏，开发者工具不报 |
| 图片 / 样式引用的资源存在 | 真机是一块留白 |
| 主包体积逼近 2MB | 超了直接传不上去 |
| 用了隐私接口却没在隐私指引里声明 | 审核必拒 |
| `console.log` 残留 | 内部调试信息打到用户设备 |

退出码 = FAIL 条数，`0` 才允许提审。当前状态：**9 通过 / 0 失败**。

**设计原则：预检必须是零判断的。**「通过 / 不通过」由脚本给，不由人看输出后自己判断——一旦需要人判断，就会开始"这次应该没事吧"。

## 五、高危区专项护栏

有些模块改坏的代价特别大，单独加护栏：

| 模块 | 为什么高危 | 护栏规模 |
|---|---|---|
| 课程表作息 | 改了作息会重排用户已录入的课表；踩过两次 | 9 套，单套最多 6,340 条断言 |
| 解析引擎 | 共用底层，所有输入路径都经过 | 四套大数据 + 语料集 |
| 隐私授权 | 错一次就等于提审被拒 | 专项检查项 |
| 数据导入 | 覆盖写入 = 用户数据丢失 | 预览 + 去重 + 回滚 |

**高危区的提交纪律**：单独提交，不与其他改动混在一起。这样出问题时能定位到具体一笔，`git revert` 一击命中。

---

## 六、包体红线

主包硬上限 2MB。项目把**余量 80KB** 设为红线，当前 82.3KB——贴着线走。

这不是洁癖。包体是**单调约束**：每次加功能都在消耗余量，等发现超了再优化，代价远大于持续盯着。逼出来的决策包括：

- 图标用字体或 SVG 而非 PNG 位图
- 样式复用优先，不复制粘贴 WXSS
- 公共逻辑下沉 `utils` 按需引入，不做全量打包
- 新增功能前先问「能不能不加代码实现」

---

## 七、这套体系实际挡下了什么

上线前后共捕获并修复 40+ 项问题，其中几类只在回归层才可能出现：

- **历史数据导致整页打不开**：旧格式记录缺字段，新代码直接崩。单测里造的数据都是"正确"格式，永远测不出来
- **导入覆盖本机记录**：批量导入时去重键选错，把已有数据顶掉
- **课表重复导入叠加**：同一份课表导两次，节次翻倍
- **作息被重排**：调整推导逻辑后，用户已保存的作息被重新计算覆盖

这四类错误的共同点：**只在"数据已存在且格式混杂"时才发生**。它们解释了为什么这个项目最终长出了一整套回归体系——不是一开始就规划好的，是被打出来的。
