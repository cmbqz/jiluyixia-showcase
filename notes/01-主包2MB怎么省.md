# 小程序主包 2MB：一个真实项目是怎么贴线走的

微信小程序主包硬上限 **2MB**（2,097,152 字节），超了传不上去，没有例外。

一个 19 页的项目，实测 **2,012,883 字节**，余量 **84,269 字节 ≈ 82.3KB**。也就是说，再往里加约 20 个中等页面就会爆。

这篇是做这个项目过程中攒下的具体手法和真实数字，不是通用建议。

---

## 一、先搞清楚 2MB 里装了什么

不要凭感觉优化。第一步永远是拆账：

```bash
# 总体
find miniprogram -type f -printf '%s\n' | awk '{s+=$1} END {printf "%.1f KB\n", s/1024}'

# 按类型
find miniprogram -type f | sed -E 's/.*\.//' | sort | uniq -c | sort -rn

# 最大的 10 个文件
find miniprogram -type f -printf '%s %p\n' | sort -rn | head -10
```

这个项目的实际结果：

| 类别 | 体积 | 占比 |
|---|---|---|
| **代码 + 样式 + 配置**（js/wxml/wxss/json） | 1,770.1 KB | **88%** |
| 图片（png/jpg） | 195.6 KB | 9.7% |
| 其他 | ~46 KB | 2.3% |

**结论反直觉：图片不是大头，代码和样式才是。**

很多人第一反应是「图片太大了要压缩」，压缩完发现只省了几十 KB。真正的重量在样式表里。

单文件 Top 5：

```
135.3 KB   wxss/caticons.wxss         ← 分类图标（彩绘皮肤）
125.2 KB   utils/parser.js            ← 解析引擎
121.3 KB   wxss/caticons-line.wxss    ← 分类图标（线稿皮肤）
 88.8 KB   pages/tasks/tasks.js
 83.0 KB   pages/schedule/schedule.js
```

## 二、最有效的单项：图标不进包

这个项目有 **179 个分类图标**，还带两套视觉皮肤（彩绘 / 线稿）。

如果用 PNG：
- 64×64 的图标约 2–4 KB/个
- 179 个 × 3 KB × 2 套皮肤 ≈ **1,074 KB**

直接把半壁江山吃掉。

### 实际做法：SVG 转 data-URI 内嵌进 WXSS

```css
.ic-cat-coffee {
  width: 100%; height: 100%;
  background-image: url("data:image/svg+xml;base64,PHN2ZyB4bWxucz0i...");
  background-repeat: no-repeat;
  background-position: center;
  background-size: 64% 64%;
}
```

179 个图标 × 2 套皮肤，两个 WXSS 文件合计 **262,750 字节 ≈ 256.6 KB**。

平均每个图标每套皮肤 **约 0.73 KB**，比 PNG 方案省了约 **75%**。

### 怎么生成的

这两个文件**不手写**，由脚本生成，文件头写明了：

```css
/* 分类图标 · 彩绘（墨线 + 物件色块）—— 由 tools/build_icon_skins.py 生成，不要手改
 * 179 个图标，SVG data-URI。类名 ic-cat-xxx 会被写进用户分类数据，**不可改名**。
 * 皮肤切换靠外层 .sk-line 作用域覆盖（见 caticons-line.wxss），不换类名。
 */
```

生成脚本做三件事：读图标源文件 → 压 SVG → 输出 base64 到 WXSS。

### 这套做法的代价，说清楚

**不能 tree-shake。** 180 个 class 全量下发，用户只用到 5 个分类，另外 175 个也一起进包了。

但对这个场景仍然划算：
- 换成图片，网络请求或本地文件都要占 1MB
- 换成分包，图标是跨页共用的，拆不开
- 换成字体图标，颜色靠 `color` 控制，做不了两套多色皮肤

**关键点：这套方案省的不是「网络流量」，是「包体配额」。** 前者可以用 CDN 解决，后者只能靠减体积。

## 三、代码怎么能到 1.7MB

19 个页面，JS 9690 行 + WXML 3024 行 + WXSS 2827 行。压缩前约 1.7MB。

三个真实原因：

### 1. 业务逻辑确实厚

`parser.js` 125KB 单文件。这不是臃肿——它承载了中文输入解析的全部规则：优先级链、19 组量词白名单、日期归一、分类词表、规格单位排除。这类**枚举型知识本身就是体积**，没有更小的写法。

能做的只有：拆成多个模块按需 require（但微信的打包并不做 tree-shaking，拆了不一定省）。

### 2. 每页四件套的固定成本

19 页 × 4 个文件 = 76 个文件。每页 json 几十到几百字节，累计也有几十 KB。

**优化方向**：公共配置抽出来，页面 json 只留差异项（`navigationBarTitleText` 之类）。

### 3. 样式重复

24 个 wxss 文件。页面之间大量重复的卡片、按钮、间距样式。

**优化方向**：抽到 `app.wxss` 或用 `@import`。注意——`app.wxss` 是全量下发的，抽错了反而更大。判断标准：**被 3 个以上页面用到的样式才值得抽**。

## 四、图片：195KB 里能省的部分

这个项目图片只占 9.7%，说明大头已经被图标方案消掉了。剩下的是 4 个角色形象 PNG + 1 个头像 JPG。

可做的：

| 手法 | 效果 |
|---|---|
| PNG → WebP | 通常省 25%–35%，但注意基础库版本兼容 |
| 按实际显示尺寸导出 | 显示 200×200 却存了 600×600，是常见浪费 |
| 角色形象改分包 / 云存储 | 只在「形象坊」页用，可下沉分包 |
| 去掉没在用的图 | 项目里 `.image-backup-` 目录有 7 张历史素材，**没在 `miniprogram/` 内**，不占包体 |

⚠️ 提醒：**图片放 `miniprogram/` 外面 ≠ 不占包体**。只有放在项目根目录、且不被页面引用，才真的不进包。用 `preflight` 检查资源引用能避免「删了图但代码还引用」的白屏。

## 五、被低估的两个手段

### 分包

主包上限 2MB，但**整个小程序上限 20MB**（主包 + 分包合计）。

这个项目**没有分包**——19 页共享同一份 store 和 utils，拆开会导致主包和分包各带一份公共代码，反而更大。

什么情况该分包：
- 有明确的功能孤岛（例如「形象坊」「图库」只在设置里进）
- 首屏用不到的页面超过 5 个
- 主包已经逼近上限且确实压不下去

分包的真实成本：**跨包不能直接 require**，要通过主包的公共模块或事件通信。这是架构级改动，不是打包配置。

### 定期体检，而不是等爆了再修

这个项目把余量 **80KB** 设为红线，写进提审前的检查项。

理由很实际：**包体是单调增长的**。每次加功能都在消耗余量，等发现超了再优化，代价远大于持续盯着。

红线的作用不是「提醒你快超了」，是**在新功能立项时就逼出「能不能不加代码实现」这个提问**。这个项目因此砍掉过两个「锦上添花」的小功能。

## 六、可以直接抄的检查清单

提审前跑一遍：

```bash
# 1. 总字节数
find miniprogram -type f -printf '%s\n' | awk '{s+=$1} END {printf "%.1f KB / 2048 KB 余量 %.1f KB\n", s/1024, 2048-s/1024}'

# 2. 最大的 10 个文件
find miniprogram -type f -printf '%s %p\n' | sort -rn | head -10 | awk '{printf "%7.1f KB  %s\n", $1/1024, $2}'

# 3. 图片总量
find miniprogram -type f \( -name "*.png" -o -name "*.jpg" \) -printf '%s\n' | awk '{s+=$1} END {printf "%.1f KB\n", s/1024}'

# 4. 找出没被引用的资源
#    逐个文件名 grep wxml/wxss/js，零命中的就是孤儿文件
```

然后人工看三件事：

- [ ] 最大的那个文件，是不是枚举型知识（该留）还是重复代码（该抽）？
- [ ] 有没有超过 100KB 的图片，实际显示尺寸是多少？
- [ ] 有没有只在一两个页面用的资源，能不能下沉？

## 最后一句

**2MB 不是一次性任务，是一个会持续收紧的约束。**

真正有用的不是「怎么省」，是**把余量做成可观测的数字，并且给它定一条红线**。没有红线，每次都能说「这次应该没事」；有了红线，才会在写代码之前先算账。
