# 加了字段，老用户打开就白屏：存量数据的三个坑

小程序迭代时最容易出的一类事故，不是逻辑写错，而是**新代码假设了新的数据格式，但用户的手机里存着旧数据**。

这类 bug 有个共同特征：**单元测试永远测不出来**，因为测试里造的数据都是"当前格式"的。它只在你上线之后、在真实用户身上爆发。

---

## 一、三个真实事故

### 事故 1：新增字段，统计页整页白屏

**现象**：给记录加了一个字段，账单页正常，统计页打开就白屏。

**定位**：统计页在 `onShow` 里遍历全部历史记录做汇总。旧记录没有这个字段，读出来是 `undefined`，参与运算后抛异常，整个页面渲染中断。

**根因**：读取侧没有做缺字段兜底。

---

### 事故 2：批量导入把本机记录覆盖了

**现象**：从微信/支付宝导出 CSV 导入后，本机原有记录被顶掉。

**根因**：去重键选错。用「日期 + 金额」判断是否重复时，同一天同金额的两笔不同消费被判成"重复"，导入逻辑选择了**覆盖**而不是**跳过**。

**真正的错**：批量写入这种不可逆操作，没有人工确认环节。

---

### 事故 3：同一份课表导两次，节次翻倍

**现象**：用户重复导入同一张课程表，每天节次变成两倍。

**根因**：导入按「追加」语义实现，每次 push，没有判断"这节课是不是已经有了"。

**真正的错**：同一个数据结构有两种合法语义（追加 / 替换）时，没有显式选一个，也没让用户知道选的是哪个。

---

## 二、为什么单测抓不到

单元测试的写法通常是：

```js
test("汇总计算正确", () => {
  const records = [
    { date: "2026-11-01", amount: 28, category: "餐饮", tags: [] },
    { date: "2026-11-02", amount: 15, category: "交通", tags: [] },
  ];
  assert.equal(summarize(records).total, 43);
});
```

问题在于：**`tags: []` 是你现在才想到要加的。**

半年前存进去的记录长这样：

```js
{ date: "2026-08-15", amount: 28, category: "餐饮" }   // 没有 tags
```

`summarize()` 里只要有一句 `r.tags.join(",")`，线上就炸。

**测试数据永远是"理想格式"，真实数据永远是"历史沉积"。** 这是结构性缺口，不是测试写得不够多。

## 三、三道防御

### 防御 1：读取侧一律兜底

**规则：不要把 `storage` 里读出来的对象当成满足当前 schema 的。**

```js
// ❌ 危险
const tags = rec.tags.map(t => t.trim());

// ✅ 安全
const tags = Array.isArray(rec.tags) ? rec.tags.map(t => String(t).trim()) : [];
```

不是加一层 try-catch——**try-catch 会让错误变成静默的空数据**，用户看到的是"我的标签没了"，比白屏更难排查。

正确做法是**在每个字段上给默认值**，让数据流下去是完整的、语义正确的。

### 防御 2：入口做一次格式归一

在读数据的入口（通常是 `store` 层）做一次性迁移：

```js
function normalizeRecord(rec) {
  return {
    id: rec.id || genId(),
    date: rec.date || "",
    amount: Number(rec.amount) || 0,
    category: LEGAL_CAT[rec.category] ? rec.category : "其他",
    tags: Array.isArray(rec.tags) ? rec.tags : [],
    deleted: rec.deleted === true,
  };
}
```

**两种防御的分工**：
- 归一（迁移）解决"以后都干净了"
- 兜底（默认值）解决"还没归一的那条路不崩"

两个都要，因为归一可能漏掉某些入口。

### 防御 3：回归用旧格式数据

这是最关键的一条，也是最容易被忽略的：

**测试数据里必须包含旧格式样本。**

```js
test("旧格式记录不会让页面崩溃", () => {
  seedStorage({
    records: [
      { date: "2026-08-15", amount: 28, category: "餐饮" },        // 三个版本前
      { date: "2026-09-20", amount: 15, category: "交通", tags: [] }, // 两个版本前
      { date: "2026-11-01", amount: 43, category: "餐饮", tags: ["午饭"], deleted: false }, // 当前
    ],
  });
  page("stats");   // 不抛异常即通过
  page("ledger");
  page("calendar");
});
```

断言的重点不是"结果对不对"，而是**"没抛异常"**。这类测试的价值在于拦住崩溃，不在于验证业务。

## 四、批量写入的四段式

事故 2 和 3 的教训，后来固化成所有批量操作的模板：

```
预览  →  确认  →  写入  →  可回滚
```

| 阶段 | 具体做什么 | 拦住什么 |
|---|---|---|
| **预览** | 展示「将新增 N 笔 / 跳过 M 笔重复 / 替换 K 条」 | 用户不知道会发生什么，误操作 |
| **确认** | 用户点「确定」才执行 | 不可逆操作没有刹车 |
| **写入** | 单事务语义，失败不留半成品 | 写到一半崩了，数据变脏 |
| **可回滚** | 写入前自动快照，提供撤销 | 写错了还有救 |

**这套模板的成本很低，但能避免一整类「用户数据没了」的事故。** 用户数据丢失是不可挽回的信任损失，比任何功能 bug 都严重。

## 五、语义必须显式

事故 3 的本质不是代码错，是**语义不清**。

课表导入有两种合理理解：

- 追加：我可能分批导入，每次加几门课
- 替换：课程表是一份完整文档，重导就是重来

**两种都合理，所以必须选一个，并且让用户在操作前知道选的是哪个。**

这个项目最终选了「整张替换」，因为「追加」会让重复导入变成数据翻倍，而用户重导的动机往往是"上次导错了"。

配套做了三件事：
1. 导入前提示「将替换现有课表」
2. 提供「仅导入到空表」的保守路径
3. 课表链路加独立护栏（9 套，单套最多 6,340 条断言）

## 六、自查清单

每次改动数据结构之前，问自己：

- [ ] 这个字段是新增的吗？**已存在的记录没有它会怎样？**
- [ ] 所有读取点都兜底了吗？（不只是主要的那个页面）
- [ ] 在 `store` 入口做了归一吗？
- [ ] 测试里加了**旧格式**的样本吗？
- [ ] 如果涉及批量写入，有没有预览、确认、快照？
- [ ] 这个操作是追加还是替换？用户知道吗？

---

## 最后一句

回头看这三个事故，能归纳成一条：

> **大多数"改坏了"，不是逻辑写错，而是对"输入是什么样"的假设错了。**

代码逻辑可以 review，假设没人 review——因为它不在代码里，在写代码那个人的脑子里。

**防御的位置也因此很清楚：在边界处不信任输入。** 读存量数据要兜底，批量写入要预览，开放集合要用白名单而不是黑名单。

这套东西不是一开始设计出来的，是被事故一个一个打出来的。区别只在于：**打完之后有没有固化成测试和红线。** 固化了的，同一个坑不会踩第二次；没固化的，半年后还会重新踩。
